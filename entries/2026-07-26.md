No coding work; short 3-question round instead of the usual full quiz.

**Learned:**
- An agent is defined by two things: its **environment** (what it perceives/acts within) and its **set of actions/tools**. These two constrain each other bidirectionally: the environment limits what actions are even possible (chess board -> only valid chess moves are meaningful; no web search tool makes sense there), and conversely, a narrow action set confines what environments the agent can usefully operate in (an agent whose only action is swimming is confined to water; a chess-only agent is useless for stock trading).
- Agents typically need more powerful models than non-agent use cases, for two reasons: **compound mistakes** (per-step accuracy compounds across steps, e.g. 95% per-step accuracy drops to ~0.95^10 ≈ 60% over 10 steps) and **higher stakes** (write actions, e.g. database mutation, bank transfers, root access, mean a failure has real consequences, not just a wrong prediction). The compounding math is the concrete reason Huyen argues planning should be decoupled from execution and validated before running (so a bad long plan doesn't silently burn time/cost before anyone notices), and why reflection/error-correction after each step matters more as step count grows, catching drift early is cheaper than discovering it at step 10.
- **Reflection failure** is a distinct and more dangerous failure mode than a tool-use failure. A tool-use failure (invalid function call, wrong parameters) produces something observable, an error, an exception, that a monitoring system can catch. A reflection failure (Huyen's example: told to assign 50 people to 30 hotel rooms, the agent assigns 40 and insists the task is complete) produces nothing, the agent's own self-evaluation is wrong, so there's no error signal and the corrective loop never triggers, the agent just stops in a "done" state. This is why Huyen recommends a separate evaluator (a distinct check or model) rather than letting an agent grade its own success: self-grading is exactly the blind spot that lets this kind of failure through.
- Other structural pieces from the post worth having on hand: tools split into knowledge augmentation (retrieval, web browsing, avoiding staleness), capability extension (calculators, code interpreters, translators, fixing known model weaknesses), and write actions (the risky category). Planning should be decoupled from execution and validated (heuristics or an AI judge) before running. Control flow for plans can be sequential, parallel, if/branching ("routing"), or for-loop/repeat, not just a linear chain of steps.

**Confused by:**
- Initially described the reflection-failure detection problem as needing to "catch the hallucinations," which is the right general category but imprecise as a mechanism. More precisely: the failure is in the agent's *self-evaluation step itself* being miscalibrated, it under-checked its own work (never verified all 50 assignments actually completed) and reported success anyway. "Hallucination" describes the symptom broadly; the actual fix Huyen proposes is structural (a separate evaluator role), not "detect hallucinations better" in the abstract.
