## Project #2 - agentic RAG (src/agent.py)
Turned the fixed retrieve->generate chain into a LangGraph StateGraph where the LLM decides WHEN to search:
- Retriever wrapped as a @tool (search_docs); llm.bind_tools([...]).
- Graph: START -> agent -> tools_condition -> (tools -> agent)* -> END. tools_condition routes to the tool node iff the last AIMessage has tool_calls, else END.
- MemorySaver checkpointer + thread_id for per-conversation memory.
Now three flavors of the same system: rag.py (fixed chain), chat.py (conversational), agent.py (agent). Production default = chat/chain for predictable single-answer queries; agent for multi-hop / compositional questions that need reasoning about what to retrieve.
Caveat: tool-calling needs reliable structured output; gemma4:e4b can be flaky at emitting valid tool calls - may need gemma4:12b.

## LangGraph concepts learned
- State = shared typed snapshot; nodes return PARTIAL updates merged by reducers. messages uses the add_messages reducer (append), so nodes return just the new message(s).
- ReAct loop via tools_condition: checks whether the last AIMessage has tool_calls -> route to tools, else END.
- Checkpointer (MemorySaver) persists state each step -> memory + resume + time-travel; thread_id SCOPES which conversation the state belongs to (same id resumes, new id = fresh). MemorySaver is in-memory; SqliteSaver/PostgresSaver for durable.
- @tool: signature + docstring become a JSON schema passed to the LLM; the docstring is the description the model uses to decide when/how to call it (write it like a prompt).
- recursion_limit (default 25 super-steps) is the runaway guard; raise it in config for legitimately long runs, and design the graph to terminate before it.
- Agent tradeoff: flexible (skip/iterate retrieval) but stochastic, slower, costlier, can misfire/loop -> keep constrained chains for predictable workloads.
