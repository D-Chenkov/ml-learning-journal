- Convolution, what a kernel actually computes at each sliding position: element-wise multiply against the underlying patch, **then sum** those products into a single scalar (a dot product, plus usually a bias), one value per position in the output feature map. That scalar is a similarity score, high means the patch strongly matches whatever pattern the kernel has learned (an edge, a texture, etc.), low/negative means it doesn't. The full computation is multiply-then-sum, not multiplication alone.
- Convolution vs. fully-connected, two real structural differences: (1) weight sharing, the same kernel weights are reused at every spatial position, versus a fully-connected layer's independent weight per connection; (2) spatial structure preservation, convolution operates directly on the image's 2D layout, while a fully-connected layer requires flattening to a 1D vector first, discarding spatial adjacency information the kernel exploits.
- Dynamic computation graphs (PyTorch's define-by-run model): the execution graph is built fresh on every forward pass rather than compiled once ahead of time (a static graph). This means ordinary Python control flow (`if`/`for`/`while`, even `print`/breakpoints) can live directly inside `forward()`, enabling variable-length sequence handling, conditional branching/skipping of layers based on input, or variable recursion depth, none of which a static graph framework can express without dedicated graph-control-flow operators. It also means debugging works with normal Python tools directly on the forward pass, no separate "compile the graph" step blocking inspection of intermediate values.
- "Model Inspecting and Debugging" concrete technique (paired with yesterday's single-batch-overfit): overfitting a single batch catches structural bugs (broken backprop, bad loss, logit/label mismatches, bad preprocessing) that let training run to completion without ever actually learning, distinct from just checking final accuracy at the end.
