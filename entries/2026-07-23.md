**Learned:**
- Covered: Introduction to Data Pipelines, Data Access, Transform Pipelines, DataLoader, Bugproof Pipelines, Quiz 1, Data Management (code), graded Quiz 2, and the "Building a Robust Data Pipeline" programming assignment.
- `Dataset` vs. `DataLoader`, division of labor: `Dataset` owns single-item access, storage/pointers to the underlying data, `__getitem__`/`__len__`. `DataLoader` owns everything at the batch level: batching, shuffling/sampling, multiprocessing (`num_workers`), and collating variable-shaped items into a uniform batch tensor.
- The actual reason to use `DataLoader`'s multiprocessing instead of a manual loop: it's CPU-side parallelism (multiple worker processes reading/transforming data concurrently), used to prefetch the next batch while the GPU is busy training on the current one. The point isn't "hand this off to the GPU," it's keeping the GPU fed so it's never sitting idle waiting on data. A naive single-process loop calling `dataset[i]` serially would starve the GPU with idle wait time between batches, that's the concrete cost, not "using the wrong hardware."
- "Bugproof Pipelines" concrete technique: **overfit a single batch**. Isolate one training batch and run the optimization loop against just that batch repeatedly. Loss should converge to near-zero (or accuracy to ~100% for classification) within a handful of iterations, since a correctly-wired model with correct backprop should be able to trivially memorize a few examples. If loss plateaus, oscillates, or barely moves on a single batch, that's a structural bug, not a data or capacity problem: broken backprop, wrong loss computation, logit/label shape or ordering mismatches, or corrupted preprocessing. This catches exactly the kind of bug that runs to completion without crashing but silently never actually learns.
